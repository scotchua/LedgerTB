## Q2. What does renumbering cost?

`create_tables` sorts full filenames, keys `schema_migrations.version` by the complete filename stem, and skips only an exact stem already recorded (`database/schema.py:34-54`). A rename is therefore normally a new migration. The protection described near the top recognizes exactly one comment-stripped `ALTER TABLE ... ADD COLUMN ...;`; if rerun fails with the exact duplicate-column message, it records the new stem and continues (`database/schema.py:12-31, 73-95`). It proves only that one named column exists. It does **not** validate type, check constraint, table identity, other statements, indexes, data, or equivalence; it deliberately excludes multi-statement and `CREATE TABLE` migrations. Scott's tests encode both boundaries (`tests/test_schema_migrations.py:165-210`).

### Option A — renumber Scott's 022–024 to unused numbers

Use `043_account_grouping.sql`, `044_cash_flow_section.sql`, and `045_document_audits.sql` (preserving their relative order). Existing books with the old stems will see all three as new. The two account migrations are each a single `ADD COLUMN`, so the narrow duplicate-column recovery records 043/044 automatically; no data migration or manual `schema_migrations` fixup is needed, assuming the actual driver emits the exact expected message. `document_audits` is multi-statement `CREATE TABLE` plus indexes and is ineligible: it will fail at `CREATE TABLE document_audits`. It needs a one-time tracking-row reconciliation (prefer a deliberately implemented/tested compatibility migration or installer step; otherwise a manual insertion of `045_document_audits` after verifying the complete table/index schema). No data migration is needed because no schema/data transformation is intended.

Future upstream sync cost is lowest: Charlie's filenames remain byte-for-byte authoritative. Scott carries one permanent fork renumber plus the compatibility treatment for already-shipped Scott books; later upstream migrations can be accepted normally unless Charlie independently reaches 043–045, at which point Scott must renumber again or reserve a fork range.

### Option B — renumber Charlie's 022–024 as they land

Use 043–045 for Charlie. Existing Scott books have never applied Charlie's old filenames, so they simply execute the new files: no data migration and no tracking fixup. Fresh books do likewise. However, any book that has already run Charlie's originals (for example a production/upstream book later opened by the fork) behaves differently: `business_context` can self-heal because 022 is a single `ADD COLUMN`; `app_preferences` and the five-table recurring migration will rerun and fail, requiring verified tracking-row fixups for their new stems. No data migration is needed if schemas match.

This option makes **every future sync harder**: every comparison with authoritative upstream retains three intentional path/name differences, migration tests must translate the three stems/count expectations, and any upstream code/document/tool referring to 022–024 must be checked. The recurring cost is at least a three-file migration-name mapping on every sync, rather than Option A's fork-local historical reconciliation.

### Option C — keep all six colliding filenames unchanged

Because tracking uses full stems and Q1 proves independence, retain both `022_*`, both `023_*`, and both `024_*`. Existing databases apply only the three missing stems; fresh databases apply all six lexicographically. No data migration and no manual tracking fixup are needed.

This is technically the cheapest behavior, but it institutionalizes duplicate numeric versions. It conflicts with tooling and human expectations that the prefix is unique, makes the loader docstring's “numeric prefix” description misleading (`database/schema.py:34-37`), and increases the chance a future migration audit or packaging script incorrectly deduplicates by number. Future syncs have no filename patch, but every schema review must remember that 022–024 are non-unique.

## Q3. Where do the features genuinely overlap?

### Earnings attribution and statement classification

Charlie's `42ac264` changes balance-sheet earnings, Close Map balances/fingerprints, and close-package tie-outs. It excludes `Beginning Balance` and `Closing` entries from current-period income and routes their P&L legs to retained earnings; ordinary current-fiscal-year activity remains Current Year Earnings (`upstream/main:models/reports.py:992-1055`; commit `42ac264`). Close Map similarly switches Revenue/Expense from life-to-date balance to period ordinary activity (`upstream/main:models/close_map.py`, commit `42ac264`). Scott's engines post ordinary journal lines into the same `journal_entries`/`journal_entry_lines`, so inventory COGS, depreciation, payroll expense, invoice revenue/sales tax, credit memos, and AR/AP activity will be presented under Charlie's subtype/grouping and earnings rules. The amount-generating engines are not recalculated by Charlie; their presentation and period attribution are.

The main clean-merge risk is Scott's `account_grouping` and `cash_flow_section`: Scott groups statement lines in `models/reports.py:43, 651-704, 1011-1037` and overrides cash-flow classification at `models/reports.py:1226-1431`, while Charlie's `f6ccd3b` changes subtype normalization, income-statement headings, and cash-flow presentation labels in the same reporting domain. The intended composition is grouping within Charlie's statement sections and honoring Scott's explicit cash-flow override before Charlie's labels. That must be inspected, even if Git resolves it. There is no evidence Charlie directly reads or removes either Scott column.

Both sides compute net income in different surfaces already: Scott uses the income statement for cash flow, dashboard, MCP report output, book review, and close-package tie-outs (`models/reports.py:1299-1341`, `services/mcp_tools.py:425`, `services/close_package.py:714-716`); Charlie separately derives synthetic Current Year Earnings and Close Map period balances. Charlie explicitly adds a close-package equality check between income-statement net income and Current Year Earnings (`upstream/main:services/close_package.py`, commit `42ac264`). This is intentional cross-checking, not a second engine, but any filter mismatch produces inconsistent figures.

### Recurring entries versus immutable posted journals

The migration-header claim is verified. `generate_occurrence` constructs a `DraftEntry`, calls `draft.save`, and links it in `recurring_occurrence_drafts`; it never creates or saves a `JournalEntry` (`upstream/main:services/recurring_entries.py:308-438`). A journal is posted only when a human approves the draft through `DraftEntry.approve`; scheduled reversals are also drafts and post only on approval (`upstream/main:models/draft_entry.py`, commit `35e25b2`; `upstream/main:tests/test_recurring_entries.py`, especially `test_adjusting_approval_posts_with_aje_and_creates_one_reversal`). Thus generation does not violate Scott's 041 human-immutability rule. The approval integration changes transaction boundaries in `DraftEntry.save/approve`, so retain Scott's immutability/reversal tests as a checkpoint.

### Schema migration test overlap

Charlie does touch `tests/test_schema_migrations.py`. His branch asserts an exact ordered list ending with his three filenames and an exact count of 24 (`upstream/main:tests/test_schema_migrations.py:27-55`). Scott currently asserts his exact list through 042 and count 42 (`tests/test_schema_migrations.py:25-60`). A naive merge cannot preserve either assertion. Under recommended Option A it must assert all 45 stems, lexicographically ordered, and count 45; it must also add upgrade coverage for the renamed Scott migrations. Under Option C it would assert 45 stems including duplicate numeric prefixes.

No irreconcilable schema divergence was found, so the escalate condition does not fire. Remaining semantic uncertainty: this was hand-traced, not executed, and report composition after textual resolution cannot be proven until the merged suite and representative engine fixtures run.

## Q5. What could tests miss?

- A client book may contain the old Scott schema but a missing or hand-edited `schema_migrations` row; exact-message healing may differ under `sqlcipher3`, and 045 cannot self-heal.
- A partially or manually created `document_audits` table could be incorrectly marked reconciled unless its columns, checks, foreign keys, and three indexes are verified first.
- Report fixtures may not combine engine-produced entries with account grouping, cash-flow overrides, non-calendar fiscal years, Beginning Balance/Closing entries, and reversals; clean code can still mis-present real balances.
- UI pages and packaged builds may access `business_context`, `app_preferences`, or recurring tables before migration completion, or retain stale cached report shapes.
- Charlie changes MCP contracts (including draft type exposure and some result shapes); external assistants may depend on Scott's prior JSON despite local contract tests.
- `version.py` moves from Scott's 1.5.0 to upstream 1.7.0; installer/backup compatibility, changelog, telemetry, and any version-gated book behavior need a release review.

## RECOMMENDED OPTION

Choose **Option A**: keep production-authoritative Charlie filenames unchanged and renumber Scott's three migrations to 043–045 before merging upstream. Its named cost is one permanent fork-side rename, test updates, and a one-time, schema-verified `schema_migrations` reconciliation for existing books' `document_audits` (the two single-column migrations self-heal). This is more work now than retaining duplicate prefixes, but it keeps every future upstream sync intelligible and avoids permanently translating Charlie's production history.
